01 · Getting started

Start here

You have been given a ZIP containing only your files. Your job is to put those files into the shared GitHub repository, in six small days, one feature at a time.

The one sentence version

For each day: pull → copy that day's files from the ZIP into the cloned folder → git add . → git commit → git push. Then do the same for the next day.

That is the entire workflow. No branches. No Pull Requests. Everything goes directly to main, exactly like Numan does.

04 · Git basics

Where your files go

Copy, don't move. (Move korleo pera nai ashole UwU)

Keep the ZIP extracted somewhere outside the repository — for example on your Desktop — so you can copy from it again for each of the six days.

The layout you are copying into

Your cloned ExpiryWise folder already contains Numan's files. Your job is only to add your own into the same folders: 

ExpiryWise/
│
├─ src/
│  └─ main/
│     ├─ java/com/expirywise/
│     │  ├─ controller/                    # your controllers go here
│     │  ├─ dao/                           # ShoppingListDAO.java
│     │  ├─ model/                         # ShoppingItem.java
│     │  ├─ service/                       # ShoppingListService.java
│     │  └─ util/                          # ThemeManager.java
│     └─ resources/
│        ├─ css/                           # dark.css
│        └─ fxml/                          # your four .fxml files
│
├─ pom.xml                                 # Numan's
└─ .gitignore                              # Numan's

What to copy, and when

You do not copy everything at once. For each day, you copy only that day's files. The next section explains the cycle, and each day section lists exactly which files belong to it.

Why copy files in small batches?

Each batch becomes one clean commit. When Numan reads the history later, he sees "Added shopping list data layer" and then "Added shopping list screen" instead of one giant commit with 13 files that says nothing.

How to copy without breaking folders

1
Open both folders side by side On the left: your extracted ZIP. On the right: the cloned ExpiryWise folder.
2
Select this day's files in the ZIP Use the file list in the day section below.
3
Drag them into the respective folder in the clone How? In the ZIP file I sent you, you may find the file "ShoppingItem.java". Now, based on everything you have read above, I hope you have an idea of where you need to copy this file, right? You need to copy/move this file into the cloned repo ExpiryWise. But, exacly where inside ExpiryWise?
Just go a little above to Section 3. Here, you can see the full path of the ShoppingItem.java file, which is src/main/java/com/expirywise/model/ShoppingItem.java. So, in the cloned repo, navigate to src/main/java/com/expirywise/model/ and paste ShoppingItem.java there.

That's it! Do the same thing for all the files in the next six days :D
05 · Git basics

The daily cycle

This is the loop you repeat for every one of your six days. Learn it once and the rest of the handbook is just variations on it.

1

Pull first

Download anything Numan pushed since you last worked.

git pull --rebase origin main
2

Copy this day's files from the ZIP

Into the cloned repository, preserving the folder structure. The day section below tells you which files.

3

Stage everything new

Because you only copied this day's files, git add . stages exactly the right set.

git add .
4

Check what you staged

Look at the green list. It should match the file list from the day section — nothing more, nothing less.

git status
5

Commit

Save the snapshot with the exact message given in the day section.

git commit -m "message"
6

Push

Upload the commit to GitHub so Numan can see it.

git push origin main

The whole cycle in one block

git pull --rebase origin main
# (copy this day's files from the ZIP into the cloned folder)
git add .
git status
git commit -m "Your message"
git push origin main
Why git add . is safe here

Numan's files are already committed, so they will not be re-staged. The .gitignore he set up keeps target/ and expirywise.db out. And you only copied your own files. So git add . stages exactly the files for this one day.

What a successful push looks like

Enumerating objects: 8, done.
Counting objects: 100% (8/8), done.
Delta compression using up to 8 threads
Compressing objects: 100% (5/5), done.
Writing objects: 100% (5/5), 1.42 KiB | 1.42 MiB/s, done.
Total 5 (delta 2), reused 0 (delta 0), pack-reused 0
To https://github.com/fardinnuman/ExpiryWise.git
   a1b2c3d..e4f5g6h  main -> main

The important part is the last line: main -> main. That means GitHub now has your commit.

Quick review

Your part, at a glance

Your 13 files, the daily cycle, and your six days — condensed into one page.

Why we are doing it this way?

Okay, so main page e onek vugichugi ase. Let me explain it simply here.

Basically, this is a team project for our university, right? So there are many files. I've already completed the whole project, but now we both have to show that we worked on it as a team. So we'll divide the parts between us. You will work on the shopping list, notifications, calendar, settings, and the diagram part. I'll handle the other parts, okay?

We could have just uploaded all the files to my GitHub and then submitted the GitHub link to mam. But that wouldn't really show that we worked on the project as a team, right? So we need to take our respective parts and upload them ourselves.

Now, another thing comes in. Let's say I take 50% of the files (e.g. five files) and you take the other five files. If I upload all five files in one day and you do the same, then that doesn't really make sense. Keno? Because anyone who looks at the GitHub history or commit history will see that we uploaded all the files in just one day. It might look like we did everything in one day, which doesn't make any sense at all.

So what we're going to do is, we use this week and next week to gradually upload the files. I've given you several files based on the different features. I think there are around 13 files in total.

What you're going to do is spread them out over several days. So you'll do Day 1, then Day 2, then Day 3, and so on. For example, on Day 1, you might upload three files. On Day 2, you might upload two files. On Day 3, you might upload another two, and so on. You get the idea.

Then comes another part: the commit!

Basically, when you upload a file to GitHub, you need to write a message describing what changes you made / what you edited / why you created the file / what the file does. That message is called a commit message.

You don't have to worry too much about the commits, but you do need to write them because we want to show that we worked on the project professionally. So we should write proper commit messages.

And to make things easier for you, I've already written the commit messages you should use for each file. For example, if you look at Day 1, you'll see which files you're supposed to add and which commit message you should use for each one. Everything is already given in this handbook, on the main handbook page.
